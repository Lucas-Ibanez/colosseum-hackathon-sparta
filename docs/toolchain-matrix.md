# Matriz de compatibilidade D1a.1

Data da correção: 2026-09-28.

Esta matriz registra somente o que fontes oficiais ou arquivos do tag exato demonstram. Ela não registra instalação local nem execução do VeriCode.

## Significado dos status

- **verificado por fonte:** uma documentação ou release oficial declara a relação registrada.
- **verificado por manifest:** um manifesto, lockfile ou workflow do tag exato registra a versão; isso não equivale a teste local nem a compatibilidade entre raias.
- **a confirmar por spike:** falta evidência oficial ou execução reproduzível para a combinação necessária ao VeriCode.
- **incompatível:** uma fonte demonstra incompatibilidade. Nenhuma das interseções abaixo recebeu este status: o problema atual é ausência de comprovação, não incompatibilidade demonstrada.

## Interseção entre as raias

O `counter` demonstra uma estrutura com dois workspaces Cargo, mas isso é apenas isolamento de compilação:

- o workspace Anchor contém o programa e a crate `shared`;
- o workspace zkVM contém host e methods/guest;
- a CPI cruza a fronteira por instruções, account metas, discriminadores, Program IDs e bytes serializados, não por “compatibilidade automática” entre workspaces;
- os dois lados precisam concordar sobre seal, journal, ImageID e Borsh; o exemplo resolve Borsh `0.10.4` para o código compartilhado, enquanto o lock zkVM também contém Borsh `1.5.7` para outras dependências;
- o spike deve provar os bytes da interface e a CPI com os lockfiles preservados. Separar diretórios não resolve divergência de CLI/SBF nem valida deployment.

Não há fonte que demonstre incompatibilidade definitiva entre Agave `2.1.0` e os crates resolvidos pelo Router. Também não há fonte que demonstre coexistência. O status correto é **a confirmar por spike**.

1. Reproduzir o `counter` do tag `v3.0.0` em ambiente descartável, registrando o commit resolvido, locks, versões de Rust/Agave/Anchor e saídas reais.
2. Testar a raia oficialmente recomendada pelo Anchor (`0.31.1` + Agave `2.1.0`) contra o código do tag, sem alterar os lockfiles; se falhar, registrar a falha.
3. Comparar com a raia do workflow (`0.31.1` + Agave `2.3.9`) sem transformar esse resultado em recomendação oficial do Anchor.
4. Fixar explicitamente a toolchain Rust do exemplo, eliminando o `stable` e a action `@main` como base de reprodução.
5. Provar a interface CPI/serialização entre workspaces e documentar os bytes críticos.
6. Selecionar uma versão exata de Docker antes do primeiro `cargo risczero build` e do gate de receipt.

Até esses gates fecharem, não criar `rust-toolchain.toml`, `.anchorversion`, `Anchor.toml`, `Cargo.toml`, lockfiles ou scaffold do VeriCode.
